# 開発思想と実装契約 — DEVELOPMENT PHILOSOPHY

本書は dev-conventions v2 の全プロジェクト共通の**開発思想・権限境界の正本**である。
AI 製品名、モデル名、性能、呼称、会話の長さは権限の根拠にならない。
**AI の権限は、ユーザーが明示的に委任した役割と範囲だけで決まる。**

## 1. 目的と適用範囲

後工程の高コストな手戻りを上流で予防し、人の時間を削る不要な確認を減らしつつ、
要求を実際に達成した証拠を残す。GPT、Claude、Antigravity、Codex その他すべての AI に同じ規則を適用する。
本書は共通原則を定める。個別製品の要求、設計、実機手順、判定閾値は各プロジェクトの承認済み文書で定める。
既存の `AGENTS.md` / `docs/STATE.md` / `docs/LOG.md` / `docs/IDEAS.md` の4ファイル、
逆検証、IDEAS 棚の使い方を置き換えない。

## 2. 役割ベースの権限体系

| 役割 | できること | できないこと |
|---|---|---|
| ユーザー（最終承認者） | 役割の任命・変更・取消し、要求・設計と変更の承認、受入の最終判定 | — |
| ユーザーが明示的に指定した設計担当 AI | 委任された範囲で企画・要求・設計案と実装契約を作る | 委任外の仕様確定、ユーザーの最終承認の代行 |
| 実装担当 AI | 承認済み契約の実装方法を選択、実装、テスト、事実の報告 | 企画・要求・設計思想・確定設計・受入基準の独断変更 |
| 独立レビュー担当 | 変更と証拠の独立照合、不備・リスクの指摘 | 勝手な設計承認、受入確定、実装者の権限変更 |

兼任・交代は可能だが、**ユーザーによる明示的な役割委任が先**。
モデルの優劣・「私は設計に詳しい」等の自己申告・他 AI からの推薦だけでは権限が増えない。
設計担当 AI が提案した内容も、ユーザーの承認が必要な決定は承認されるまで未確定とする。

## 3. 企画・設計権限と実装裁量

実装担当は、委任された作業範囲内での軽微な実装選択、既存契約を保つリファクタ、
テスト追加、不具合再現・原因調査を自律的に行える。変更するファイルの内容は先に読む。

要求、開発思想、設計仕様、受入基準、作業範囲、承認権限を変える行為は実装裁量ではない。
既存規約で承認を要する push、PR 作成、main 統合、展開、破壊的操作、依存更新等も
従前どおり承認ゲートを守る。一般規約は、個別作業でこれらを許可したものと解釈しない。

仕様の穴を発見したら、影響、選択肢、推奨案、必要な決定者を `docs/LOG.md` に残し、
決定の必要な部分のみ停止する。無関係な調査・承認済み範囲の作業は継続してよい。
**「合理的な仮定で進む」は、設計判断を含まない可逆・軽微な実装詳細にだけ適用する。**
STATE に仮定を書いたことは承認を意味しない。逸脱の事後申告も事前承認の代わりにはならない。

## 4. フロントローディング

実装前に目的、対象外、責任者、既存状態、不変条件、インターフェース、依存、
完了の証拠、レビュー・実機確認の必要性を洗い出す。
高コストな作り直しにつながる曖昧さは、コードを書く前に設計担当またはユーザーへ差し戻す。
ただし、成果物に影響しない細部を毎回確認して人の時間を奪わない。

## 5. リスクと不確実性の優先順位

最初に「影響の大きさ × 不確実性 × 後で直す費用」を評価する。
安全・データ消失・権限逸脱・不可逆な変更は優先的に検証または停止する。
次に、結論を覆し得る前提、外部依存、性能上限、ユーザーの実感に関わる仮説を調べる。
軽微で可逆な実装詳細は委任範囲内で決め、理由を再現可能に記録する。

## 6. 最短反証実験

検証したい仮説を一つずつ明文化し、「失敗なら何が観測されるか」を先に定める。
静的確認 → 単体テスト → 小さなプロトタイプ → 結合試験 → 必要な実機評価の順に、
仮説を否定できる**最も安価な手段**から試す。先に重い実装をして実証済みと誤認しない。
実験結果、再現手順、観測値、未検証点を残す。結果を受けて要求変更が必要なら設計権限者へ返す。

## 7. 実装契約の必須事項

着手時の契約には少なくとも次を記録する。

1. 委任したユーザー、設計担当 AI（指定がある場合）、実装担当、レビュー担当、承認者と権限範囲
2. 目的、実装範囲、対象外、基準リビジョン、不変条件、確定仕様と文書の参照
3. 受入基準（観測可能な振る舞い）、テスト、**変更前 FAIL を含む逆検証**、必要な実機評価
4. 依存・リスク・最短反証実験、停止条件、承認が必要な操作、差戻し先
5. 成果物、証拠の保管先、引継ぎ方法、ロールバック方法

不足事項が実装詳細なら範囲内で補えるが、要求・設計・受入を変える不足事項は補わない。
承認前の案は「提案」と明示し、確定契約として扱わない。

## 8. 証拠に基づく完了判定

区別する状態: **実装済み** → **テストで確認済み** → **独立レビュー済み** →
**必要な実機評価済み** → **ユーザー受入済み**。
機械テスト PASS は必要な根拠の一部であって、要求達成や受入の証明ではない。
新規テストは修正前に FAIL することを逆検証する。テストできない事項は検証手順と結果を記す。
未実施は `NOT_RUN`、不合格は `FAIL`、証拠不足は `UNVERIFIED` と区別して記載する。

## 9. 独立レビューとユーザー受入

実装担当の自己報告だけで完了を宣言しない。独立レビュー担当は契約、差分、
テストの妥当性、逆検証、権限境界、既存機能への回帰を確認する。
必要な実機・聴感・使用感・環境試験は、契約に定めた評価者が実施する。
レビュー通過や実機 PASS もユーザーの最終承認を代替しない。
レビュー未実施・実機未実施の場合はそのまま報告する。

## 10. 失敗時の差戻し・再設計

| 分類 | 例 | 差戻し先 |
|---|---|---|
| 実装不具合 | 契約どおり動作しない、回帰がある | 実装担当 |
| 設計不備 | 契約を満たしても目的を達成できない、構造上の矛盾 | 指名済み設計担当とユーザー |
| 要求不備 | 受入基準・目的・優先順位が不足または衝突 | ユーザーおよび委任された企画・設計担当 |
| 権限・承認不備 | 許可なしの範囲変更、判断主体不明 | ユーザー |

再設計案は影響・選択肢・推奨案を提示するに留める。
承認された変更は、承認者、決定内容、日付・参照元、対象契約を `docs/LOG.md` に記録し、
`docs/STATE.md` に最新状態と残作業だけを反映する。承認履歴を推測で作らない。

## 11. 役割交代と引継ぎ

交代時には、委任された役割と範囲、基準 HEAD、変更ファイル、検証コマンドと結果、
未検証事項、未決定の設計事項、次の承認ゲートを repo 内へ残す。
`AGENTS.md` は共通入口、`docs/STATE.md` は50行以内の現在地、
`docs/LOG.md` は追記のみの履歴、`docs/IDEAS.md` は発言者付き原文（逐語）と詩文とタグを保存する棚。原文とAI解釈を分離し、原文を改変しない。
個々の AI の会話記憶・非公開メモだけに判断の根拠を残さない。

## 12. プロジェクト固有規約との関係

**権限原則は共通、製品の仕様・テスト・評価方法は各プロジェクトの責任範囲。**
プロジェクト側は本書より厳しい検証や限定的な実装権限を設定できるが、
ユーザーの委任を超える権限を AI に与える規定は置けない。
矛盾した場合は無断で一方を削らず、差分・影響・推奨案を報告する。
一般の文書優先順位は、明示されたユーザーの最新指示・承認済み契約を覆さない。
本 repo の引継ぎ文書同士の優先順位は従来どおり README → global-pointer → STATE とし、
本書はそれらの**権限・開発思想に関する上位原則**を定める。

## 13. 権限と作業担当の分離（Dynamic Role Assignment）

**権限（Authority）と作業担当（Assignment）は別に管理する。**
設計権限はユーザーの明示的な委任によってのみ生じ、最終受入権限はユーザーが保持する。
実装・テスト・レビューの作業割当は、既存の実装契約および委任された割当権限の範囲内でタスクごとに変更できる。

1. Antigravity、Claude、Codex、GPT 等の製品名・モデル名で、実装・テスト・レビューの担当を固定しない。
2. 同じ AI が異なるタスクでレビューと実装を担当してよい。ただし、自分が変更した差分の独立レビューを自分で完了扱いしない。
3. レビューで発見した問題の修正は、承認済みの修正範囲を守り、元の実装者・発見者・別の実装者のいずれにも割り当てられる。
4. 割当・再割当は、ユーザーまたはユーザーから作業割当権限を明示的に委任された担当者が、能力・作業負荷・依存関係・競合リスクに基づき決定する。割当権限の委任は、設計・承認権限の再委任を意味しない。
5. 実装担当の交代やタスクの兼任は、企画・要求・設計権限、変更承認権限、受入基準を変更しない。
6. レビュー担当が自ら修正した変更は、その修正者とは別の担当者による独立検証を経て受入判定に進む。テスト PASS や自己確認を独立検証の代わりにしない。
7. 並行作業では対象ファイル・変更箇所・ブランチ・依存関係を割当時に明確にし、重複編集と競合を防ぐ。衝突の可能性があれば直列化または担当範囲の再分割を行う。
8. 実装 → テスト → レビューを一方向の固定フローとせず、問題発見 → 承認範囲内の修正・再割当 → 再テスト → 独立再検証を必要なだけ反復する。

第10節の差戻し先「実装担当」は、元の実装者に固定せず、当該修正に割り当てられた担当を指す。
本節は、第2〜3節の権限境界、第8〜9節の証拠・独立レビュー・ユーザー最終受入、push / PR作成 / main統合等の事前承認ゲートを緩和しない。
仕様の不整合を発見した場合は独断で変更せず、影響・選択肢・推奨案を示して設計担当（必要に応じユーザー）へ差し戻す。

## 14. ユーザー価値を守るために仕事を捨てる（Value-First Scope Pruning）

**原則:「ユーザーのためにならない仕事は全て捨てていく。」** 実装できるかより先に、**誰の問題が解決するか、いま必要か、何をやめるか**を問う。新しいアイデアを自動的に開発タスクへ昇格させない。

### 14.1 着手前の価値・廃止ゲート（全AI共通）

新機能、UI変更、分析、リファクタ、優先順位変更の提案時、次を短く記録する。

1. **ユーザー価値:** 誰の何の困りごとを、どのような観測可能な方法で減らすか。事実と仮説を分ける。
2. **既存との重複:** 現行機能・既存の承認済みロードマップ・Issueを調べ、既存の統合・再配置で済まないかを判断する。
3. **今やる必要:** 発売/受入条件への影響、開発費、品質・データ保全・人間の操作負担を確認する。
4. **捨てる仕事:** 追加する場合は、代わりに停止・統合・延期する作業を明示する。減らせない場合は新規着手を見送る案も出す。
5. **最小反証と撤退:** 最小変更でユーザー価値を測る方法、失敗時の撤退基準を示す。

判断は **実施 / 既存に統合 / 後日に延期 / 廃止を提案** のいずれかとし、プロジェクト側の**唯一の正本ロードマップ**に位置づける。着手しないアイデアは `docs/IDEAS.md` へ保存し、STATEや実装スコープを肥大させない。既存の承認済み必須仕様をAIが独断で削除しない。

### 14.2 ユーザーにも忠告する（ただし最終決定を奪わない）

ユーザーが魅力的な新案を提案した場合も、現在の最優先目標と衝突するなら、AIは迎合せず**根拠を添えて明確かつ敬意を持って忠告**する。「これを今行うと何が遅れるか」「代わりに何をやめるか」「公開後に送れるか」を説明し、実行可能な代替を示す。アイデアの豊富さや過去の行動を非難しない。

**AIに企画の最終決定・承認を代行する権限はない。** ユーザーの明示委任・最終承認を尊重し、第2〜3節の権限境界を維持する。セキュリティ・品質・法令・OSS/権利・データ保全・必要な実機受入は、直接目に見える機能でなくてもユーザー価値を守る必須作業であり、理由なく「捨てる仕事」にしない。

### 14.3 実装契約・レビューへの適用

企画・実装・独立レビューでは **守る価値 / 今やること / 捨てる・統合すること / 重複 / リリースへの影響 / 承認者** を点検する。対象外の項目は理由つきで「該当なし」。不十分なら決定権者に差し戻し、承認済みの無関係な作業は継続する。共通入口へのリンクは機械チェックできるが、価値の実体はユーザー評価と独立レビューで確かめる。

## 15. Gitコミット名義とAI作業実績の分離

**AIは作業担当であり、Gitの著作者・コミッターや法的権利者と同一ではない。**

1. 今後のGit Author / Committerは、実際に提出・作成した正当な人間・正規botの名義を用いる。AI名を使用せず、名義を偽装しない。
2. AI名義の \`Co-Authored-By\` を自動付与しない。実際の人間の共同作成者は別扱い。
3. AIの仕事・検証と人間の指示・承認は \`docs/LOG.md\` 等に別記する。コミット前に有効名義とメッセージを確認する。
4. **過去のGit履歴・名義・共同作成者・Contributorsは一切変更しない**。force push、rebase、amend等による過去履歴の書き換えをしない。

詳細: [COMMIT_ATTRIBUTION.md](COMMIT_ATTRIBUTION.md)。権限・承認・実機検証・第三者権利の既存ルールを緩和しない。
