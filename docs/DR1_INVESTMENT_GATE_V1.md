# DR1 Investment Gate v1.0 — 詳細設計

- 文書種別: DR1専用・事業投資審査システムの詳細設計
- Version: 1.0 proposal
- Status: **設計レビュー待ち（未発効）**
- Scope: 新規商用製品・新市場参入・大幅な事業モデル変更に対するDR1のみ
- Policy authority: docs/DEVELOPMENT_PHILOSOPHY.md §16.4
- Related protocol: docs/DEVELOPMENT_PHILOSOPHY.md §17

> **目的はプロジェクトを通すことではない。市場に勝てる合理的な証拠があるかを調べ、なければ開発投資を止めることである。**
>
> 本書はDR1を機械的・再現可能に審査するための設計案である。v1.0としての正式採用は、本書のレビューとユーザー承認を経てPRをmainへ統合した後とする。統合前に本書の配点・閾値を正式な審査結果へ適用してはならない。

---

## 1. 設計原則

1. **ユーザーの意見も例外なく検証する。** 創業者の希望、経験、予測、既存の決定、投資済み工数を特別扱いしない。AIの提案も同じ証拠基準で検証する。
2. **意見と証拠を分ける。** 主張は仮説台帳に登録し、支持証拠・反証・未確認事項・反証条件を記録する。
3. **魅力度と証拠の強さを分ける。** 「魅力がありそう」と「それを裏付ける証拠が強い」を同じ点数に混ぜない。
4. **事前登録する。** 目標利益、到達時期、許容時間・費用、配点、合格閾値を結果を見る前に固定する。
5. **事業モデルごとに分ける。** コンサルティング、ソフトウェア、受託開発、広告等の売上・粗利・獲得費用を混ぜない。
6. **人間の時間を無料扱いしない。** 開発・営業・提供・保守・サポート・法令対応の時間を機会費用として計上する。
7. **不明は不明とする。** 非公開の競合売上、架空の転換率、根拠のない継続率を補完しない。
8. **多数決で決めない。** GPT・Claude・ユーザーの意見はそれぞれ検証し、結論が割れた場合も反対意見を保持する。
9. **DR1だけを厳格化する。** DR2〜DR6や通常保守へこの100点制度を一律適用しない。
10. **正式GO以外は次の正式開発段階へ進めない。** PENDING中に許可するのは、上限と終了条件を事前登録したDR1内の調査・反証実験だけ。

## 2. 適用範囲と非適用

### 2.1 適用する案件

- 新規の商用ソフトウェア・アプリ・サービス
- 新しい顧客層・業界・地域への本格参入
- 既存製品の収益モデル・販売経路を大きく変更する場合
- 開発・営業・保守の時間を大きく割り当てる新規事業
- 既存事業を別の市場・顧客層へ横展開する際、投資判断が必要な場合

### 2.2 適用しない案件

- 通常のDR2〜DR6
- 小さな不具合修正・保守・既に承認された範囲内の改善
- 市場収益を目的としない個人用・社内用の小規模ツール。ただし、その場合も利用価値・維持費・時間コストは別途定量化する
- 既にGO済みの事業に対する通常の機能追加。ただし市場・事業モデルを実質変更するなら再DR1を行う

適用の要否で迷う場合は、投資額だけでなく、不可逆性・開発時間・顧客約束・継続運用負荷で判断する。

## 3. 審査ステータスと権限

### 3.1 DR1の正式判定

| 判定 | 意味 | 次の正式開発段階 |
|---|---|---|
| GO | 採点・証拠水準・全必須ゲートを満たした | DR2へ進行可 |
| PENDING | 重要証拠・数値・事前条件が不足、または未検証 | **進行不可**。DR1内の限定調査のみ |
| REWORK | 顧客・価値・価格・販売経路等の仮説を組み直す必要がある | 進行不可。修正後にDR1を再審査 |
| STOP | 十分な検証の結果、投資基準を満たす勝ち筋がない | 中止。新しい市場・モデル等の重要な変化があれば新DR1 |
 
**DR1ではCONDITIONAL GOを使用しない。** 重要条件が未達なのに「条件付き」で次工程へ進む抜け道を作らない。通常DRのCONDITIONAL GO規則はDR1には適用しない。

### 3.2 権限

- ユーザーは事業の所有者であり、GO後の投資実行、PENDING継続、STOPを決定できる。
- ただし、審査基準を満たさない結果を「GO」と記録する権限は、通常のDR1手続きには存在しない。
- ユーザーが「通せ」と指示しても、証拠・点数・必須ゲートが不合格なら判定エンジンはPENDING/REWORK/STOPを返す。
- AIはGOを承認しない。AIは独立評価・批判・計算確認を行い、正式判定は事前登録されたルールと証拠から算出する。
- ユーザーはいつでも作業を止められる。STOPやPENDINGを選ぶ自由は常に残る。
- 判定基準の変更は個別案件の判定変更と分離し、§12の規約改定手続きを通す。

## 4. 事前登録（審査開始前に固定する項目）

次の項目が未設定なら、審査を開始しても正式GOにはできない。

| 項目 | 必須内容 |
|---|---|
| 事業目的 | 誰の何の問題を解決し、どの価値を提供するか |
| 最初の顧客 | 利用者、購買者、予算保有者、決裁者を区別 |
| 最初の市場 | 業界・規模・地域・利用状況を具体化 |
| 主たる収益経路 | 初期に検証する主経路を1つ指定。副経路は別採点 |
| 目標利益 | 月/年の営業利益または事業所得、税引前/後の定義 |
| 到達期限 | いつまでに目標利益へ到達するか |
| 稼働上限 | 週当たり・月当たりの開発、営業、提供、保守時間 |
| 現金上限 | 初期費用・月次費用・累積費用の上限 |
| 機会費用 | 代替できる仕事・案件・休息の価値と比較方法 |
| 事業期間 | 原則5年間の予測と成熟後の継続シナリオ |
| 合格閾値 | 本書の初期基準を採用するか、採用前に改定するか |
| 中止条件 | どの証拠・数値ならSTOPするか |

結果を見てから目標利益・期限・時間上限を緩めてはならない。変更が必要な場合は、変更理由・影響・承認・新しい版を記録し、既存の不利な結果を消さない。

## 5. 100点評価モデル

### 5.1 配点

| No. | 評価軸 | 配点 | 主な問い |
|---:|---|---:|---|
| 1 | 顧客課題の深刻度・頻度 | 15 | 頻繁で経済的に痛い問題か |
| 2 | 顧客・到達可能市場 | 10 | 購買者を特定し、現実に接触できるか |
| 3 | 競合に対する差別化 | 15 | 既存手段より明確な優位があるか |
| 4 | 支払意思・有償需要 | 20 | 実際に予算を使う顧客がいるか |
| 5 | 収益性・ユニットエコノミクス | 15 | 人間の時間を含めて利益が出るか |
| 6 | 顧客獲得経路・CAC | 10 | 繰り返し顧客を獲得できるか |
| 7 | 継続利用・長期事業性 | 10 | 4〜5年目以降も需要・利益を維持できるか |
| 8 | 提供実現性・運用負荷 | 5 | 品質・セキュリティを保ち無理なく提供できるか |
| | **合計** | **100** | |

### 5.2 各軸の魅力度評価（0〜5）

点数は「証拠が示す事業上の魅力度」であり、証拠の強さそのものではない。各点数には必ず証拠IDを紐付ける。

| 点 | 共通の意味 |
|---:|---|
| 0 | 価値が確認できない、または反証されている。未調査の場合も保守的に0とし、E0と明記 |
| 1 | 弱い兆候のみ。一般論・創業者の見立て・競合の宣伝情報が中心 |
| 2 | 一部の対象顧客で具体的な問題・利用意向が確認されたが、規模や再現性は不明 |
| 3 | 複数の独立した対象顧客で問題・価値・購入条件が確認され、実行可能な販売仮説がある |
| 4 | 実証・有償行動・比較評価で優位性と経済価値が確認され、複数顧客に再現している |
| 5 | 複数顧客・複数期間で成果、支払、継続、採算が再現し、持続的な優位が確認されている |

軸ごとの採点補助:

1. **課題:** 0=問題なし/反証、1=漠然とした不満、2=個別の不便、3=反復する問題と損失、4=優先度の高い経営課題、5=複数顧客で重大損失と購入優先度を確認。
2. **市場:** 0=顧客不明、1=TAMだけ、2=ICPと市場データあり、3=購買者・予算・接触可能な顧客群を特定、4=複数チャネルで商談到達を確認、5=再現性のある顧客獲得経路を複数確認。
3. **差別化:** 0=既存手段で十分/優位なし、1=機能一覧やAI搭載だけ、2=独自ワークフロー仮説、3=複数顧客が特定業務で優位を確認、4=比較実証で成果・時間・コスト優位、5=継続的に再現する優位・運用定着・切替コスト等を確認。
4. **支払意思:** 0=支払拒否/需要なし、1=褒め言葉・無料希望、2=価格を伴う口頭意向、3=具体的な見積・予算・調達プロセス、4=独立顧客による有償購入、5=複数顧客の再購入・更新・紹介を伴う有償利用。
5. **収益性:** 0=現実的なシナリオで赤字/目標未達、1=価格だけの仮説、2=費用を含む概算モデル、3=実測工数・費用を含む損益分岐モデル、4=実案件で時間原価込みの正の貢献利益、5=複数顧客・期間で利益を再現。
6. **顧客獲得:** 0=経路なし、1=個人的な期待のみ、2=顧客リストとアウトリーチ計画、3=実際の反応・商談・転換率を測定、4=CACと回収期間を実測、5=複数チャネルで安定獲得。
7. **継続性:** 0=一回限りで再需要なし、1=継続仮説のみ、2=繰り返す業務課題を確認、3=再利用・再依頼の行動を確認、4=更新・継続率を複数期間測定、5=コホート等で長期継続・拡張を確認。
8. **提供・運用:** 0=法令/セキュリティ/技術上成立しない、1=重大な未解決事項、2=試作で実現可能性を確認、3=代表的な実務で品質・工数・データ取扱いを検証、4=安定した提供手順とサポート工数を確認、5=品質を保った標準運用と低い限界費用を再現。

### 5.3 点数計算

- 事業魅力度スコア = Σ（各軸の配点 × 魅力度点 / 5）。0〜100点。
- 未調査・根拠なしは魅力度0点・証拠E0とする。これは「市場が存在しない証明」ではなく「価値を立証できていない」という意味である。
- 点数は小数第1位まで保持し、丸め前の値で判定する。
- 手計算やAIの印象点を正式値にしない。機械計算スクリプトがscorecardから再計算する。

## 6. 証拠の強さ（魅力度点とは別に採点）

| 等級 | 定義 | 例 |
|---|---|---|
| E0 | 証拠なし、出典不明、再現不能 | 願望、未確認の伝聞 |
| E1 | 二次情報・間接情報 | 公的統計、競合公式機能表、公開価格、創業者の過去経験 |
| E2 | 一次情報による顧客発見 | 対象購買者への構造化ヒアリング、実際の購買手順・損失の記録 |
| E3 | 行動・実証の証拠 | 許可を得た実データ実証、比較試験、具体的な予算・調達行動、利用ログ |
| E4 | 支払と継続行動 | 入金済みの有償契約、再購入、更新、複数期間の継続利用 |

### 6.1 証拠指標

- 証拠強度 = Σ（各軸の配点 × E等級 / 4）。0〜100点。
- 一次証拠カバレッジ = E2以上の証拠がある軸の配点合計。0〜100%。
- すべての軸に証拠ID・出典・取得日・対象母集団・方法・限界を記録する。
- 公開統計や競合資料は市場背景・競合比較には使えるが、個別顧客の支払意思を証明しない。
- 創業者自身の成功体験は能力・ドメイン適合性の証拠にはなるが、新製品の需要・再現性・顧客の支払意思の証拠にはならない。
- 同じ顧客・同じ案件・同じデータを複数証拠として重複計上しない。
- 口頭の「欲しい」「使いたい」は支払いではない。非拘束のLOI、アンケート、待機リストはE4にしない。

## 7. 必須ゲート（点数とは独立）

全ゲートがPASSでなければGOにしない。NOT_VERIFIEDはPENDING、実証された不成立はFAILとして扱う。

| Gate | 必須条件 | 最低証拠 |
|---|---|---|
| G0 事前登録 | 目標利益・期限・稼働/費用上限・主収益経路・機会費用・中止条件が結果を見る前に固定 | 承認済みDR1 Charter |
| G1 顧客課題 | 購買者・利用者・予算保有者を分け、反復する課題と経済損失を確認 | 原則、対象購買者10名以上の構造化調査。少なくとも5件で反復課題、3件で損失額または代替支出を具体化。例外サンプルは独立レビューで妥当性確認 |
| G2 到達可能市場 | TAMだけでなくSAM/SOM、対象顧客リスト、接触経路、購買プロセスを説明 | 出典付き市場推計、実在する対象顧客群、一次情報 |
| G3 差別化 | 上位3つの競合・代替手段（Excel/内製/Python等を含む）と比較し、顧客が価値を認める未充足課題を特定 | 原則3名以上の独立顧客による確認と、少なくとも1つの比較実証または実務ワークフロー評価 |
| G4 有償需要 | 主収益経路で実際の購入行動を確認 | 下記7.1の経路別条件 |
| G5 採算 | 時間原価込みの単位採算、損益分岐、目標利益到達シナリオが成立 | 実測工数/費用または保守的な根拠付き範囲。悲観/標準/楽観の5年モデル |
| G6 顧客獲得 | 接触から契約までの現実的な経路とCAC/回収期間を示す | 実際のアウトリーチ・商談・成約データ。未実測値は仮定として感度分析 |
| G7 継続性 | 4〜5年目以降も需要・利益・運用能力を維持できる | 更新/再依頼/反復需要の行動証拠、保守・サポート負荷、顧客集中リスクを含むモデル |
| G8 提供・法令・データ | 提供方式、品質、安全、知財、契約、個人情報/機密情報、データ移送、外部AI利用の制約を扱える | 代表ケースの実証と未解決リスクの対策。重大な未解決法令・セキュリティ問題があればFAIL |
| G9 独立審査 | §17に従い、同一証拠でGPT/Claude等が相互開示前に独立評価し、相互批判・再評価を実施 | 初回評価、相互批判、再評価、反対意見の記録。未実施はNOT_RUN |

### 7.1 有償需要ゲートの経路別条件

DR1では最初に検証する主収益経路を1つ宣言する。副経路の売上や意向を主経路の証拠に流用しない。

- **コンサルティング/受託サービス主導:** 独立した2顧客以上から有償受注し、少なくとも1件は完了して成果・実工数・粗利を測定。さらに再依頼、契約延長、紹介経由の有償案件のいずれかを確認する。
- **SaaS/ソフトウェア主導:** 独立した3顧客以上の有料利用を確認し、少なくとも2顧客で90日以上の有料継続または更新を確認する。単発買切りの場合は複数顧客への販売再現性と紹介/追加購入を別途確認する。
- **ハイブリッド:** 初期の主経路を明示し、その経路の条件を満たす。副経路は「未検証」と表示し、事業計画上の売上を確定収益として扱わない。
- 入金、決済記録、拘束力ある契約を優先する。無償PoC、口頭の購入意向、非拘束LOIだけではG4 PASSにしない。
- これらはv1.0の初期最低値。市場特性に応じた変更は審査開始前に規約改定し、結果を見てから緩めない。

## 8. 収益モデル・機会費用の計算要件

### 8.1 収益を分離する

コンサルティング、ソフトウェア、ライセンス、保守、その他の収益を別々に計上する。ソフトウェアの売上をコンサル案件の成功で代用しない。

### 8.2 最低限の計算

- 売上 = 顧客数 × 単価 × 購入/継続回数（モデルに応じて分解）
- 粗利 = 売上 − 直接提供費用
- 貢献利益 = 売上 − 直接費用 − 顧客別サポート/提供工数の時間原価
- CAC = 新規顧客獲得に使った現金費用 + 営業時間原価 ÷ 新規有料顧客数
- LTVは実測継続率がない場合、確定値として表示しない。複数シナリオの推計幅にする。
- 損益分岐顧客数 = 固定費 ÷ 顧客1件あたりの月次貢献利益（単位・期間を揃える）
- 経済的利益 = 現金ベース営業利益 − 開発/営業/運用の機会費用
- 開発費は一度きりの費用だけでなく、保守・OS/依存更新・セキュリティ・サポート・法令対応を含める。

### 8.3 時間原価と機会費用

- 創業者の時間単価は、代替可能なフリーランス案件・同等スキルの市場単価等から保守的に設定し、根拠を残す。
- 開発時間、顧客獲得時間、提供時間、サポート時間を分けて記録する。
- 休息・健康維持も有限資源として扱い、週当たり稼働上限を超える計画を標準シナリオにしない。
- 現金支出が少ないことを「投資ゼロ」と表現しない。

### 8.4 事業継続モデル

- 原則5年分の悲観・標準・楽観シナリオを作る。
- 収益化までの期間、顧客数、単価、転換率、解約/更新、CAC、粗利、サポート負荷、開発/保守時間を明示する。
- 4〜5年目の成熟後に、顧客の残存・新規獲得・競合反応・技術更新・運用負荷を織り込む。
- 売上だけでなく、営業利益、経済的利益、時間当たり利益、最大累積赤字、損益分岐時期を示す。
- 不明な変数は幅で置き、感度分析でGO/STOPが反転する条件を示す。
- 顧客1社依存、創業者1人依存、特定プラットフォーム依存、AI/API価格変動を明示する。

## 9. 顧客調査・競合調査の実施ルール

1. 調査対象の選定条件を先に決め、都合のよい顧客だけを選ばない。
2. 顧客ヒアリングは「この製品が欲しいか」から始めず、直近の具体的な問題、損失、現在の代替手段、既存支出、決裁経路、実際の購入行動を聞く。
3. 肯定意見だけでなく、購入しない理由、導入を止める条件、競合継続の理由も記録する。
4. 競合は機能一覧だけでなく、価格、導入/運用コスト、対象顧客、販売チャネル、サポート、制約、代替手段まで比較する。
5. 競合が機能を持たないと断言する場合は、公式資料・実機・顧客利用のいずれかで確認する。
6. 公開情報の取得日・URL・対象範囲を記録し、古い情報を現在の事実として扱わない。
7. 市場規模はTAM/SAM/SOMを区別し、実際に接触できる顧客数・予算・購入頻度からボトムアップで検算する。
8. 調査担当自身の仮説に合わない回答も削除せず、反証として残す。

## 10. §17 複数AI審査の運用

- DR担当（事務局）は証拠パッケージ、採点表、論点、未解決事項を整える。DR担当と独立評価者を混同しない。DR担当は独立した新しいAI人格を意味せず、GPTが事務局を兼任してよい。
- DR担当の口調は冷静・敬意・具体性を基本とし、ユーザー本人ではなく主張・仮説・証拠を検証する。厳格さを威圧的な言い方で表現しない。
- GPTが既に同じ案件の結論や相手AIの評価を見ている場合、その会話での評価を「初回独立評価」と偽らない。GPTの独立評価が必要なら、共通証拠だけを渡した新規セッションを用意し、相互開示前に提出する。
- GPTとClaudeは同じ版の証拠パッケージを受け取り、互いの初回結論を見る前に独立採点する。
- 初回評価には、各軸の点数、証拠ID、確信度、反証、GO/PENDING/REWORK/STOP推奨を含める。
- 相互開示後、互いの採点・証拠選択・推論を批判し、各自が再採点する。変更理由を残す。
- ユーザーの主張・希望・事業計画も同じように仮説登録し、反証を探す。ユーザーが強く主張したことは証拠にならない。
- AI間の多数決・平均点で正式判定しない。採点エンジンは証拠と固定ルールから計算する。
- 同じ会話で既に相手の結論を知っているAIは、初回独立評価済みと偽らない。新しい独立セッション/評価者を用意するか、独立性欠如を記録する。
- 反対意見が残っても、必須ゲートと証拠が通っていればユーザーはリスクを理解して判断できる。ただし、反対意見を議事録から消さない。

## 11. 証拠パッケージとデータ構造

### 11.1 推奨成果物

| ファイル | 内容 |
|---|---|
| docs/dr1/charter.md | 事前登録、目標利益、期限、時間/費用上限 |
| docs/dr1/hypotheses.md | ユーザー・AI・調査担当の主張、反証条件 |
| docs/dr1/evidence-register.csv | 証拠ID、主張ID、出典、日付、対象、方法、限界 |
| docs/dr1/market-model.xlsx または .csv | TAM/SAM/SOM、顧客数、単価、到達可能性 |
| docs/dr1/competitor-matrix.md | 競合・代替手段・価格・比較結果 |
| docs/dr1/economics-model.xlsx または .csv | 5年シナリオ、CAC、LTV、粗利、時間原価 |
| docs/dr1/scorecard.yaml | 8軸の魅力度点・証拠等級・証拠ID |
| docs/dr1/reviews/ | GPT/Claude初回評価、相互批判、再評価 |
| docs/dr1/gate-result.json | 機械計算された最終点数・ゲート・判定 |

顧客名、機密データ、契約書、未公開工程データを公開Gitへ置かない。必要ならアクセス制限された保管先に置き、repoには匿名化した要約、証拠ID、ハッシュ、保管場所の参照だけを残す。顧客データの持出し・外部AI送信は明示許可がない限り禁止。

### 11.2 gate-resultの考え方

gate-resultは人が手入力する判定欄ではなく、scorecard・証拠台帳・ゲート状態・レビュー記録からスクリプトが生成する出力とする。少なくとも次を含む。

- schema_version / gate_version / project_id / review_id
- evidence_package_commit / baseline_commit
- 事前登録値と主収益経路
- 8評価軸の点数・配点・証拠等級・証拠ID
- 事業魅力度スコア / 証拠強度 / 一次証拠カバレッジ
- G0〜G9のPASS / NOT_VERIFIED / FAIL
- GPT/Claude初回評価・相互批判・再評価の記録参照
- 算出日時、スクリプト版、判定理由
- 計算結果としてのGO / PENDING / REWORK / STOP

手入力のoverride_pass、force_go、skip_gate等のフィールドを設けない。

## 12. 機械的な進行制御（GitHub CI）

### 12.1 必須チェックの設計

DR1 gateを実装する段階では、専用の決定論的スクリプトとGitHub Actions等の必須チェックを導入する。AIの自然言語判定をCIに直接渡さず、固定されたscorecardをスクリプトが再計算する。

必須チェックは少なくとも次を検証する。

1. gate_versionが承認済みバージョンと一致する。
2. 事前登録値が証拠収集開始前に固定されている。
3. 8評価軸すべてに点数・証拠等級・証拠IDがある。
4. 証拠IDが台帳に存在し、日付・出典・方法・限界が記載されている。
5. 重複証拠・同一顧客の水増し・期限後の基準変更を検出する。
6. スコアと証拠強度を規則どおり再計算する。
7. G0〜G9を再計算し、NOT_VERIFIEDやFAILをPASSへ上書きできない。
8. 独立評価・相互批判・再評価の成果物が揃っている。
9. GO条件をすべて満たさない場合、DR2の正式成果物をmainへ統合するPRを失敗させる。
10. PENDING中に許可する変更は、DR1の証拠・調査・反証実験に限定する。

### 12.2 GitHub保護

- mainにDR1専用のrequired status checkを設定する。
- DR2成果物を含むPRは、最新のGO判定IDと証拠パッケージのcommitを参照しなければならない。
- CODEOWNERSまたは別の独立レビュアーによる承認を要求する。
- 可能な限りrulesetのbypassを無効化し、管理者も通常フローを通す。
- gate判定を変更するPRとDR2移行PRを同じPRに混在させない。
- gateの基準版と判定時の基準commitを記録し、古いGO判定を新しい事業モデルへ流用しない。

**技術的限界:** リポジトリの唯一のOwner/AdminがGitHubの保護設定そのものを変更できる環境では、本人による全バイパスを技術的に完全禁止できない。実質的な強制力が必要なら、別の管理者/独立承認者、組織レベルruleset、bypass権限の分離を用いる。単独Ownerのまま「絶対に解除不能」と説明してはならない。通常運用では、バイパスを正式GOとして扱わず、逸脱記録・独立レビュー対象とする。

## 13. PENDING中に許可する活動

PENDINGは何もしないという意味ではない。ただし、正式なDR2へ進んだことにしない。

許可できる活動:
- 顧客ヒアリング、競合調査、価格確認
- 反証可能な小規模PoC・データ検証
- 有償需要を確かめるための限定的な提案・販売テスト
- 既存コードの保全、セキュリティ修正、データ保護等の必要な保守

各活動は開始前に、目的・仮説・方法・時間/費用上限・成功条件・中止条件・終了日を記録する。正式な構想設計・大規模実装・不可逆な投資・顧客への未承認約束は行わない。

## 14. 規約変更・基準の凍結

1. v1.0の配点・閾値・必須ゲートは、正式採用後、個別案件の結果を見て変更しない。
2. 基準変更は新バージョン（v1.1等）の変更提案、理由、影響分析、独立レビュー、ユーザー承認を必要とする。
3. 結果を見てから合格させるための変更は認めない。進行中のDR1には原則として遡及適用しない。
4. 市場構造や法令など外部環境が変わった場合は、変更根拠と適用対象を明記して新バージョンを制定する。
5. 旧基準での点数・証拠・反対意見は履歴として保持し、書き換えない。
6. ユーザーが審査を中止・STOPすることはいつでも可能。基準未達をGOに変える個別例外は設けない。

## 16. 受入基準

- 8評価軸と配点の合計が100点である。
- 魅力度点と証拠強度が別々に計算される。
- 事前登録値、主収益経路、機会費用、5年シナリオが必須である。
- 有償需要はコンサルティングとSaaSで別の条件を持つ。
- 必須ゲートにNOT_VERIFIEDが1つでもあればGOにならない。
- 80点未満、証拠強度70未満、一次証拠カバレッジ70%未満はGOにならない。
- G0〜G9の全PASSがGOの必要条件である。
- DR1ではCONDITIONAL GOを使わない。
- PENDING中はDR1内の上限付き調査だけを許可し、DR2へ進めない。
- ユーザー・AIの主張を同一の証拠基準で検証する。
- §17の独立評価・相互批判・再評価・反対意見記録を含む。
- 手動overrideを設けず、CIの機械判定を設計する。
- 管理者権限による技術的バイパスの限界を明記する。
- DR2〜DR6に100点制度を一律適用しない。

## 17. 初期閾値の位置づけと再校正

80点、証拠強度70点、一次証拠カバレッジ70%、顧客調査数、有償顧客数は、厳格な初期基準として提案する値であり、統計的に最適だと証明された普遍値ではない。

正式採用前に、過去の案件へ遡及して都合よく合格させるためではなく、基準の過剰/過小な厳しさを検討する。採用後の変更は§14に従う。閾値の根拠が不十分なら、v1.0の正式採用自体をPENDINGにする。

**最終原則:** DR1は、ユーザーやAIが通したい案件を通すための手続きではない。事前に固定した基準と検証可能な証拠によって、投資する価値がある案件だけを次段階へ送るための投資ゲートである。
